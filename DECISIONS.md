# Architecture Decision Records

## ADR-001: Provider-Agnostic LLM Layer
**Decision:** Abstract base class pattern for LLM clients.
**Reason:** Enable hot-swapping between Gemini, Claude, OpenAI without 
modifying core system logic.
**Status:** Implemented

## ADR-002: Separate Path Resolution from Validation
**Decision:** path_resolver.py and validator.py are distinct modules.
**Reason:** Translation and validation are different responsibilities. 
Path resolver converts logical paths to real paths. Validator checks 
safety and correctness. Mixing them would violate SRP and make 
cross-platform support harder.
**Status:** Implemented

## ADR-003: Structured Error Codes over Formatted Strings
**Decision:** Executor returns "MOVE_SUCCESS" not "Moved file X to Y".
**Reason:** Presentation is main.py's responsibility. Status codes 
enable consistent handling across CLI, GUI, API, and tests without 
changing executor.
**Status:** Implemented

## ADR-004: Batch Schema — LLM Describes Intent, App Discovers Files
**Decision:** Batch operations schema contains filter rules, not 
actual filenames. Application resolves matching files from filesystem.
**Reason:** LLM cannot reliably enumerate real filenames. Keeping 
file discovery in application code ensures we validate against 
real filesystem state, not LLM-invented filenames.
**Status:** Planned — batch operations not yet implemented

## ADR-005: Dry Run Before Batch Execution
**Decision:** All batch operations require a preview step showing 
exact before/after for every affected file before any execution.
**Reason:** Batch mistakes multiply. A user must explicitly review 
and confirm the complete operation set before any file is touched.
**Status:** Planned

## ADR-006: organize_folder — LLM Describes Intent, Python Discovers Files
**Decision:** LLM returns only {action, source}. Python handles all
file discovery, categorization, duplicate resolution, and planning.
**Reason:** LLM cannot reliably enumerate real filenames. Filesystem
state must be read from disk at plan-time, not generated by the model.
**Status:** Approved — pending implementation

## ADR-007: Batch Execution — Per-File with Partial Failure Tolerance
**Decision:** Batch operations execute per-file. Single file failure
logs the error and continues. Execution never aborts mid-batch unless
re-validation fails before the first operation.
**Reason:** Aborting on first failure leaves the folder in a partially
organized state that is harder to reason about than continuing and
reporting failures clearly.
**Status:** Approved — pending implementation

## ADR-008: Preview Threshold — 20 Files
**Decision:** Batches ≤20 files show full file-by-file preview.
Batches >20 files show category summary with expand option.
**Reason:** Full preview of 200 files is not readable. Summary gives
confidence about scope; expand option preserves transparency.
**Status:** Approved — pending implementation

## ADR-009: Batch Execution — Shared Raw Operations, Separate Orchestration
**Decision:** organizer.py imports raw filesystem operation functions
from executor.py (_move_file_raw) rather than calling shutil directly
or calling execute_command(). executor.py's public interface is unchanged.
**Reason:** Filesystem operations (shutil.move + error handling) belong
in one place. Batch orchestration (loop, real-time feedback, partial
failure collection) belongs in organizer.py. These are different
responsibilities. Sharing raw operations avoids duplication without
coupling interfaces.
**Alternative considered:** organizer.py calls shutil.move() directly.
Rejected: duplicates error handling and creates two sources of truth
for filesystem operations.
**Status:** Approved — pending implementation

## ADR-010: Domain Model — Three Dataclasses, No Redundant State
**Decision:** Three dataclasses: FileOperation, OperationPlan, BatchResult.
Derived values (total, counts) excluded from OperationPlan to avoid
redundant state. BatchResult uses @property for computed counts.
Execution results kept strictly separate from the plan — plan represents
intent, BatchResult represents outcome.
**Reason:** Redundant stored state requires synchronization and creates
inconsistency risk. A plan object that also holds results conflates
two distinct concepts.
**Status:** Approved — pending implementation
